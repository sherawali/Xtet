# Parse, validate, load, verify, report, export

**Scope:** an offline, deterministic SQLite pipeline for the five in-repository CTET Paper I texts and the pinned UTET `bank-v2` Paper I snapshot. It does not implement a frontend, API, synchronizer, CDN, hosting, or published executable.

## Quick start

Python 3.11+ and SQLite with FTS5/JSON1 are required. Install the only pinned third-party dependency (`jsonschema`) to validate the vendored UTET Draft 2020-12 data schemas:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt

python -m pipeline validate-sources
python -m pipeline build
python -m pipeline verify --db data/xtet-question-bank.sqlite
python -m pipeline export --db data/xtet-question-bank.sqlite --output-dir build/exports
```

The default deliverables are `data/xtet-question-bank.sqlite`, the single-file app download `data/xtet-question-bank.json`, `docs/DATA_QUALITY.md`, and detailed NDJSON files under ignored `build/exports/`. The JSON bundle is regenerated by every full `build` and includes a content hash so the app can identify the exact dataset. The generated staging JSON is under ignored `build/xtet-stage.json`.

## Rerunnable commands

Each stage can also run independently:

```sh
python -m pipeline parse --stage build/xtet-stage.json
python -m pipeline validate --stage build/xtet-stage.json
python -m pipeline load --stage build/xtet-stage.json --db data/xtet-question-bank.sqlite
python -m pipeline verify --db data/xtet-question-bank.sqlite
python -m pipeline report --db data/xtet-question-bank.sqlite --output docs/DATA_QUALITY.md
python -m pipeline export --db data/xtet-question-bank.sqlite --output-dir build/exports
```

`build` runs parse → stage/source validation → atomic load/migrations → database verification → report → app JSON/NDJSON export. `load` constructs a fresh database in a temporary sibling file, applies forward migrations, inserts sorted rows in FK order, verifies the completed database, and atomically replaces its target only on success. A failure leaves the previous database artifact untouched. Runs use stable IDs and no timestamps/randomness. Repeating a build with unchanged source/config/migrations produces the same relational `content_hash` and app JSON bytes; the acceptance test compares independent clean rebuilds. SQLite page bytes are not used as the cross-runtime determinism criterion.

## Stage responsibilities

1. **Source inventory and validation**
   - Verify source file bytes/UTF-8 and store path, SHA-256, byte length, pinned UTET commit, CC BY 4.0 attribution, and source URI.
   - Validate the 12 pinned UTET schemas and the 900 question rows, 900 appearance rows, 6 form rows, and 24 stimulus rows with `jsonschema==4.23.0` and local JSON Schema references.
   - Keep CTET text sources read-only. CTET validation is structural: section ranges, four-option groups, source question numbers, answer-table ranges/counts, locale blocks, reviewed mirror runs, and stimulus/question ranges. The parser does not “correct” or cross-check wording against a scanned booklet.

2. **Parse to stage**
   - CTET: read all seven `.txt` sections, `Answer-Key.txt`, and `README.md` for each of the five papers. Section headers/ranges and README metadata drive form/session structure. Passages/poems become locale-specific stimuli from source directions and explicit question ranges; numbered passage lines are not treated as question starts. A configured mirror file (`config/ctet_mirrors.json`) is a review allow-list: each build rediscovers key/content/option-compatible candidates and stops if a range changes.
   - CTET common bilingual sections retain `en` and `hi` content under one canonical question/appearance. Confirmed parallel Language I/II pedagogy runs share canonical identity but retain both source appearances and translations. Independent language/comprehension questions remain distinct. Raw answer-key tokens are preserved; A–F/Z expand to native option rows.
   - UTET: validate form module appearance lists and 30-question ranges, then connect each appearance to a canonical question row, localized Markdown prompt/options, source stimulus, audit, and source-embedded answer. Repository review fields/audit values are kept as source assertions. Those answers receive `source_repository` + `provisional`, never an official UBSE status.
   - Every fact points to source records. CTET question/key/stimulus spans and UTET original NDJSON/JSON records store exact raw text, one-based inclusive line bounds, extraction method, and `imported_from`. Original files remain available and are fingerprinted.

3. **Validate stage**
   - Reject duplicate staging keys, stale/modified source files, missing provenance, broken option/question/answer/stimulus links, missing localized option text, and unexpected counts before touching the target artifact.
   - Expected imported totals: CTET 5 forms, 930 canonical questions, 1,050 retained language/core appearances, 1,050 final-key entries; UTET 6 forms, 900 questions, 900 appearances, 900 provisional source-answer entries; combined 64 stimuli and 411 explicit stimulus links.
   - Taxonomy nodes/assignments, difficulty/Bloom ratings, explanations, assets, and human review tables start empty rather than receiving invented values.

4. **Load/migrate**
   - Migrations are sorted `NNN_name.sql` files. The loader calculates SHA-256 from migration bytes and writes the actual version/name/checksum to `schema_migrations` after successful application. Rewriting an already-applied migration is rejected.
   - Staged rows are inserted deterministically under foreign-key enforcement. FTS search documents are derived per available `(question_id, locale_code)` from the localized stem, ordered options, linked stimulus text, and approved explanations; triggers populate external-content `question_search_fts`.
   - `build_metadata` stores schema/importer versions, SQLite runtime, FTS capability, source-manifest hash, and a SHA-256 content-derived build hash over source hashes, migration checksums, importer version, and normalized rows. Machine-specific absolute paths and timestamps are excluded.

5. **Verify/report/export**
   - Verification runs `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, migration checksum comparison, source-manifest/content-hash recomputation, FTS5 external-content integrity and sample Hindi/English matches, exact form/question/appearance/key/stimulus counts, option-locale coverage, and official/provisional answer-boundary checks.
   - `report` regenerates `docs/DATA_QUALITY.md`; the report separates source assertions from independent authority proof and records the CTET README key citations (August 2023 has no direct key URL in the inspected README) and the UTET source-repository disclaimer.
   - `build` and `export` produce `data/xtet-question-bank.json`, one regular JSON document the app can download in one request. It contains `metadata`, `questions`, `appearances`, `stimuli`, `answer_key_history`, and a separate `official_final_answers` list. `appearances` carries the exam code so CTET and UTET stay distinguishable. Detailed UTF-8 NDJSON exports are also written for streaming/import use. A manifest records each export's record count, byte size, SHA-256, source-manifest hash, and database content hash. Do not treat `answer_key_history` as an authority-only feed; it intentionally includes UTET provisional source values; use `official_final_answers` for official-final answers only.

## Mirror-review data and drift

`config/ctet_mirrors.json` is deliberately explicit review data rather than parser code. Each configured run records its two locale streams, question start/end, and human-readable review basis. During parsing, candidates must have matching keys, four options in the same order, no attached stimulus, and a contiguous range at least 15 questions long. The parser compares the discovered set to the review allow-list and exits with both values on drift. Update that config only after inspecting source text and keys; the CTET `.txt` files themselves remain untouched.

## Errors and diagnostics

Parsing/schema failures are raised as `path:line: detail`, e.g. `.../questions.ndjson:24: Q17: expected four ordered options, found 3`. Form/module/key errors identify the source record, expected range/count, found values, and (where applicable) missing/duplicate question numbers. A mirror drift error identifies the form, discovered ranges, and reviewed ranges. The pipeline fails closed; it does not skip malformed rows or partially replace the verified DB.

## Tests and CI

Run the complete local suite:

```sh
python -m unittest discover -s tests -v
```

The suite schema-validates UTET, builds both exams, verifies raw provenance/source pins, answer authority classification, key expansion and localized option coverage, rebuilds twice to compare content hashes, executes all 29 SQL examples in `docs/QUERIES.md`, verifies the single-file JSON bundle, and generates a report. GitHub Actions repeats source validation, unit/integration tests, build, and verification on pushes and pull requests.

## Change protocol

- Do not edit/reformat/retranscribe source `.txt` papers, upstream source files, or generated content to make a parse pass. Resolve failures in parser/config/schema after inspecting the indicated lines.
- Pin any updated upstream source commit and preserve its license, attribution, schema files, manifests and audits. An upstream commit change creates a different source manifest and content hash.
- Never promote third-party answers to `exam_authority`/`final`. New official key versions require an authority citation and must remain separately versioned; never overwrite an older version.
- For a schema change, add a forward migration. Do not revise a released/applied migration checksum. Re-run the full CI and two-build determinism gate before delivering a new database artifact.
